# Prune Tests

`vitest.config.ts`に`coverage`設定はなく、CIはテストを実行しない。したがってどのテストが何を守っているかを機械的に知る手段がなく、テストは増える一方で減る契機がない。

一方で雑に消すと実害が出る。`5c86bce 不要なテストファイルを削除`で14ファイル2,094行を一括削除したあと、`hooks/useIME.test.ts`と`hooks/useOscSender.test.ts`は27コミット後の`0399553`で書き直されている。したがってこのskillの目的は削除量を増やすことではなく、**根拠を機械的に示せるものだけを消すこと**である。

`verify` skillとの境界: このskillは**通っているテストだけ**を対象とする。落ちているテストの扱いは`verify`の領分であり、そこでは実装を直す。

## 手順

1. 対象を決める。引数にパスが与えられていればそれ、無指定なら`**/*.test.ts`と`**/*.test.tsx`の全件。

2. `npm run test:run`を実行し、全件passであることを確認する。1件でも落ちていれば**この時点で中断し**、先に`verify`で直す必要があると報告する。落ちているテストを削除して整理したと称してはならない。

3. 各テストファイルを読み、下の「自動で削除してよいもの」「提案に回すもの」「削除してはならないもの」に分類する。

4. 自動削除分を適用する。削除は`it`単位で行い、ファイル内の`it`が全部消える場合のみファイルごと削除する。削除によって参照されなくなった`vi.mock`、モック変数、`beforeEach`、import、型定義も一緒に消す。

5. `npm run test:run`と`npm run typecheck`を再実行する。

6. 報告する。自動削除したものは`path:line`・分類・根拠、提案に回したものは`path:line`・何をどうしたいか・確認したい点。末尾に「テストが薄い箇所」を1節添える。**削除理由をファイルやコミットに残す必要はない** — 取り返しは`git diff`と`git checkout`で足りる。

## 自動で削除してよいもの

根拠がコードを読めば確定するものに限る。

- **実装に触れていないテスト** — その`it`の本文が、テスト対象モジュールからimportしたシンボルを一度も呼んでいない。実装が壊れてもパスするため回帰を検出しない。実例は`electron/services/OscBridgeService.test.ts:53-137`で、`parseChatboxMessagePayload`をimportしながら9 it中6 itが実装のロジックをテスト内のローカル変数に書き写して検証している。同じ振る舞いは`:48-51`が実装経由で検証済みでもある。
- **参照されないモック** — `vi.mock`やモック変数を宣言しているが、どの`expect`からも参照されていない。上記の削除後に残骸として残りやすい。実例は同ファイル`:14-35`の`ws`/`node-osc`モックと`mockOscSend`、および無意味になる`vi.clearAllMocks()`。
- **完全に同じassertの重複** — 2つの`it`が同じ入力・同じ期待値を持ち、片方が他方に情報を足していない。実例は`utils/throttle.test.ts:17-23`と`:80-86`(後者はデフォルト値を明示的に渡しただけ)、`:36-52`と`:106-116`、`electron/services/IpcHandlers.test.ts:81-95`の`real-world scenarios` 3 it(`:10-42`の再実行)。残すのは情報量が多い側、同等なら先に書かれている側。
- **`it.skip` / `it.todo` / コメントアウトされた`it`** — 現状0件だが、増えたら消す。

## 提案に回すもの

自動で触らず、報告して確認を取る。

- **`it.each`への統合** — 骨格が同一で入力と期待値だけが違う`it`の羅列。`utils/ime.test.ts`が最大の候補(基本母音5 it `:7-30`、ゔ系5 it `:208-238`、促音3 it `:121-137`、`convertToKatakana` 14 it `:302-383`)。統合すると個々のテスト名が失われるので、名前に仕様の説明が入っている場合は残す判断もありうる — だから自動でやらない。
- **定数をそのままassertしているテスト** — `utils/colorUtils.test.ts:109-131`の`PRESET_PALETTES` 4 it。`utils/colorUtils.ts:187`はロジックのないハードコードされたリテラルなので回帰は検出しないが、パレット定義の破壊を防ぐ意図の可能性がある。
- **テスト名が主張する内容を検証していないテスト** — `utils/throttle.test.ts:160-172`の`preserves this context`は`expect(obj.fn).toHaveBeenCalled()`しかなく、`this`が保たれたかを検証していない。`throttle`が`this`を捨てる実装に変わってもパスする。これは削除ではなく**修正**を提案する。
- **片方に過去バグの文脈があり、もう片方が包含されている重複** — `utils/ime.test.ts:114-119`は`:161-167`に完全に含まれるが、後者が属するdescribe(`:140`)には`過去バグ対象`と書かれている。この場合に消す候補は文脈のない`:114`側であり、判断を誤ると逆を消すため確認を取る。

## 削除してはならないもの

- CLAUDE.mdが名指しで「テストが固定している」と述べているもの: `hooks/useSettingsDraft.test.ts`(`useSettingsDraft`の項)。開閉エッジでの再同期と即時書き戻しという非自明な二重の挙動を固定している。
- describe名・it名・コメントに過去バグや回帰の文脈が書かれているもの: `utils/ime.test.ts:140`の`促音の中間状態（過去バグ対象）`、`hooks/useOscSender.test.ts:25`(手動送信後の二重送信)、`hooks/useIME.test.ts`(候補表示中の数字キー)、`electron/input_handler.test.ts`(コントローラー消失時のstateリーク)。
- セキュリティ境界: `electron/services/IpcHandlers.test.ts:99-111`の`isSafeExternalUrl`。
- 安全側の仕様を固定しているもの: `electron/services/ime/MozcDictionaryProvider.test.ts:200-247`(改竄シャードを隔離して他は生かす、警告は1回だけ)、`:249-264`(最適化後も候補ランキングを保つ)、`:129`(シャードキャッシュの上限)。
- **判断に迷ったら残す。** `git log --oneline -- <path>`でそのテストがどのコミットで入ったかを確認し、機能改善・修正コミットに付随して追加されていれば回帰テストとして扱う。

## 補足

- カバレッジ設定がないため、あるテストが何を守っているかは機械的には取れない。疑わしい1件を確実に判定する唯一の方法は、対象実装を一時的に壊して`npx vitest run path/to/file.test.ts`が落ちるかを見ることである。落ちなければそのテストは何も守っていない。**確認後は必ず実装を元に戻すこと。**
- このリポジトリのテストの慣習: `it`名は英語、`describe`名はスラッシュで日英併記(`describe('hexToRgb / HEXからRGBへの変換')`)、コメントは日英併記。`globals: true`だが全ファイルが`vitest`からのimportを明示している。統合や修正で書き換える際はこれに合わせる。
- `it.each`はこのリポジトリで現在0件。導入すると最初の1箇所が前例になるため、ケース表の形とテスト名のテンプレート書式を統一すること。
- `@testing-library/react`は`renderHook`と`act`のみ使用しており、`render`/`screen`/`userEvent`によるコンポーネントテストは存在しない(`5c86bce`で削除済み)。「コンポーネントテストがない」ことを欠落として報告しない。
- `.agent/rules/testfile-guide.md`はAntigravity用のファイルで、Playwrightのe2eハーネスや`main/`ディレクトリという実在しない前提に基づいている(CLAUDE.mdが両方を否定している)。このskillの判定基準に使ってはならない。
